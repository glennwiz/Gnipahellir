  **The bug was the buffer.** `log_action` wrote into a fixed 256 KB buffer and set an `overflow` flag when it filled — after which the run was simply unrecorded, and `flush_action_log` rewrote the whole file from that same buffer. Flushing now opens `action.log` in **append** mode, writes `buf[:pos]` and sets `pos = 0`; `log_action` calls the flush itself within `DEBUG_LOG_LINE` of the end. Memory stays 256 KB, the FILE grows for as long as the run does, and nothing is dropped. `overflow` is gone (nothing else read it). Proof: the new test writes 4000 lines and counts newlines in the file — the old code lands **3458 lines in 261,698 bytes**, the new one all 4000 past `DEBUG_LOG_CAP`.
  **`Debug_Log.path` is the test firewall, and it is empty by default.** Only `action_log_begin_run` (main, before the loop) arms it — it truncates `action.log` and writes the header (datetime, `SAVE_VERSION`, world seed). An unarmed log opens no file at all, so the 300-odd tests that build `Game_State`s and log freely **cannot** touch `src/action.log`, which is Glenn's playtest ground truth; the streaming test opts into a scratch path and deletes it. `game_state_init` preserves the path across a reset (the one part of the log a New Game must not lose) — the buffer itself is still dropped, as before. Verified by hashing `src/action.log` before and after the full suite: `a23ab001…c508` both times. **Loading a save mid-session does NOT truncate** — it logs its own line into the same file, because the record must keep the run that led up to the load.
  **Attribution.** `handle_tile_mined` writes one line naming the actor (`Player mines Stone at (x,y)` / `Enemy#3(Fire_Sprite) smashes Crafting_Bench at (x,y)`), and it is deliberately the *only* hook needed: the pick, the wand, a reclaim, and the raiders/sprites that call the handler directly instead of queueing all pass through it. Its three refusal branches log too — a mine that did NOT happen reads as a missing minute otherwise. `entity_name(gs, id, buf)` (debug_log.odin, into the caller's buffer, no allocation) answers "who" in one place and returns `"the world"` for the sourceless hurts (lava, falls), so a player damage line with no attacker is not a bug in the line. Deaths are explicit for player and enemy; `roll_enemy_drops` logs what actually fell; placing, ground pickups (with the count that *fit*), foraging and the Rainbow Laser's zap all got lines — the laser because it fires **as** the player and was otherwise indistinguishable from a wand hit.
  **The "all happenings" net.** `process_events` traces every event it pops — `evt <Type> src=%d tgt=%d tile=(%d,%d) val=%d` — gated by `@(rodata) event_log_skip`, which excludes exactly two entries: `.Play_Sound` and `.Projectile_Impact`, both pure audio/visual. Types with no handler and no bespoke line are traced on purpose; the one nobody thought worth announcing is the one missing when a mystery turns up. Direct handler calls bypass the trace and are covered at handler level (commit 2). **Breadcrumbs** ride the existing 300-frame flush beat: one `pos Player …` line and one `pos Enemy#%d %v (x,y) hp goal target` per live enemy every 5 s — that is what would have made the #4/#6 flyer mystery readable, and worst case is 65 lines per beat, nothing against a streamed log. `update_waves` logs the cycle position and what the next craft buys.
  **No throttling, no sampling** — Glenn asked for everything, and the streaming append is what makes that a disk-space non-issue rather than a memory one. Determinism/replay (same seed + input → same log) is the natural follow-up and was explicitly out of scope. **Not yet eyeballed in a real run:** the header line, the 5 s breadcrumbs and the file growing past 256 KB are unit-proven but unplayed — the next playtest is the acceptance smoke.

## 1. What the game is

**Gnipahellir** ("Yawning Chasm", Old Norse) — a fullscreen, grid-based 2D
Norse-underworld **mining roguelike**. Odin + Raylib, Windows primary.

- **Dual-axis loop:** descend into caves, ascend into the sky. Neither axis is
  completable alone. Descend → find a Rune Scroll → ascend → build the matching
  Sky Structure → that unlocks the next cave gate. Three tiers, then the Garm
  boss fight, then the win.
- **The player is fragile; the world is hostile.** Death is permanent
  (roguelike); persistent stats survive across runs.
- **The long arc is automation:** hands in the dirt early → architect of
  machines late → eventually *manufacture whole worlds* (dimensions) and
  strip-mine them with snake miners.
- **Design north star (Glenn's):** *the cost mirrors the reward* — pay iron to
  open an iron-rich world; the gem you feed a machine is the speed you get back.

Full design bible: `gnipa_project/plan.md`. Live issue audit: `gnipa_project/flagg.md`.

## 2. Architecture law (mandatory — full text in CLAUDE.md)

One Odin package (`game`); boundaries are call-discipline rules, checked by review.

- **Fat struct:** all runtime state in `Game_State`. No module-level mutable globals.
- **Fixed-size arrays only.** No `[dynamic]` growth during gameplay; buffers sized at startup. Full pool = silent drop (log in debug).
- **Event-driven:** systems talk via `Event_Queue`, consumed once per frame in `process_events`. No direct cross-system calls.
- **Render is read-only:** `draw_*` procs read state + call raylib, never mutate.
- **Table-driven behavior:** terrain/item/enemy/recipe = a table row. No `switch` sprawl.
- **Deterministic update order:** every system has an explicit numbered line in `game_update`.
- **Enums are append-only** (saves store them as u8). Any layout change to a saved struct → bump `SAVE_VERSION` + the size `#assert` in the same commit. There's a probe test that logs real `size_of(Save_Data)`, `len(Item)` and `size_of(Progression_State)`.
- **Never key a SAVED array by `[Item]`/`[Tile_Type]`** — size it to a ceiling like `MAX_ITEM_SLOTS` instead. An enumerated array inside `Save_Data` makes every appended enum value a silent save break (this cost a version bump on 2026-08-08). Enumerated arrays in `@(rodata)` tables are fine and encouraged.
- **Entity map** (`World_Grid.entity_map`): per-tile position index (center tile, last-writer-wins) for lookups/combat targeting — NOT a movement constraint (bodies are continuous AABBs, may overlap). Entity_ID: player = 0, enemy slot i = i+1. Despawn via `despawn_enemy`, never bare `enemy_free`.
- **No TODOs in committed code** — implement or file it here.

### Module responsibility (who may touch what)
- `render.odin` / every `draw_*` → read `Game_State`, call raylib. Never mutate, never call update/input.
- `input.odin` → polls hardware, pushes to `Event_Queue`, toggles `UI_State`, sets inventory selection (the one deliberate exemption). Never writes `World_Grid` or entity data.
- `world.odin`, `enemy.odin`, sim code → never call `draw_*` or input procs.
- `types.odin`, `game_state.odin` → shared foundation only (types, constants, fat struct); no game logic.

### Key constants (don't change without updating plan.md)
```
GRID_W 192 · GRID_H 108 · CELL_SIZE 10
MAX_ENEMIES 64 · MAX_PARTICLES 256 · MAX_PROJECTILES 32 · MAX_EVENTS 512
```

### game_update order
1 input · 2 player · 2b camera · **2c clay golems** · 3 enemies · 4 projectiles · 5 mining · 5a equipment reclaim · 5b0 power decay · 5b sim (smelters/growers) ·
**5b1 industry raids** · 5b2 miner (dimension only) · 5c station-focus · 5c2 hover-desc · 5d recipe-unlocks · **5e ritual (offering swirl)** · 5f sky apparition ·
6 process_events · **6b falling-blocks (gravity)** · **6c fluids (water/lava flow)** · 7 notifications · 8 ambience · 9 particles · 9b floating text · **9c tile fx** · 10 audio.
(update.odin is authoritative — its comments carry the ordering constraints.)
